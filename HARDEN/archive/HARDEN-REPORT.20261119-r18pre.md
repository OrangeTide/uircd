## Every finding, one line

- H-001 WARN FIXED [protocol]: An operator running KLINE on a ban that matches their own connection had uircd_ban_add free the operator's client, after which cmd_kline dereferenced it (heap-use-after-free read of c->nick). Reproduced under ASan via HARDEN/harness/kline_self_uaf. (`uircd.c cmd_kline; uircd.c:305 cli_target`)
- H-002 WARN FIXED [host-net]: No per-IP connection cap and no unregistered-session deadline: one source IP could hold up to max_clients (default 1024) slots by connecting and not registering, reclaimed only by the 120s+60s ping cycle, denying service without authenticating (`uircd.c uircd_accept (per-IP cap); uircd.c uircd_tick (registration deadline)`)
- H-003 NOTE FIXED [auth]: Response timing enumerated valid account/oper names: the KDF ran only for a name that existed with the needed flag and returned in ~1us for a miss (measured ~61ms vs ~0.001ms), also exposing oper-capable and offline names WHO does not. Fixed by async auth: the verdict is delivered at a fixed deadline+jitter on both the hit and miss path, so timing no longer separates them, and a miss runs no KDF (`example/miniircd.c on_auth, on_auth_deadline (deadline-scheduled verdict); example/auth.c auth_lookup, auth_compute (miss runs no scrypt)`)
- H-004 NOTE FIXED [protocol]: uircd_ban_add collected victims into a fixed victims[256], so a ban matching more than 256 connected clients left the rest connected until reconnect; the index was bounded so no memory unsafety, an enforcement gap (`uircd.c uircd_ban_add`)
- H-005 NOTE FIXED [protocol]: parse_term accepts a field!=glob negation and GKILL/kill_match honor it, but uircd_ban_add and client_banned matched with client_field_match which ignored negate, so a negated KLINE spec banned as if positive; now a term_matches helper applies the negation on every path (`uircd.c term_matches; uircd.c client_banned; uircd.c uircd_ban_add`)
- H-006 NOTE FIXED [repo]: No SECURITY.md: the repository gave no private route to report a vulnerability and no request to keep addresses out of reports (`SECURITY.md`)
- H-007 BLOCK FIXED [host-net]: Heap-use-after-free in the threaded host: when one fd was ready for both write and read in a single poll pass, on_io called on_writable (which could close_conn and free the conn on a write error or drained want_close) then still called on_readable on the freed conn. Reachable by any client, no auth. Found under TSan. (`example/miniircd.c on_io; example/miniircd.c on_writable; example/miniircd.c close_conn`)
- H-008 NOTE FIXED [host-net]: Data race on the shutdown flag g_stop: declared volatile sig_atomic_t, written unlocked by the main thread after sigwait and read by every worker, which is async-signal safe but not a thread synchronization and races under TSan (`example/miniircd.c g_stop; example/miniircd.c on_wake; example/miniircd.c worker_main`)
- H-009 WARN FIXED [host-net]: Descriptor-exhaustion busy-loop: on accept() returning EMFILE/ENFILE/ENOBUFS/ENOMEM the handler just broke out, but libiox is level-triggered, so a connection left queued kept the listener readable and on_accept respun at 100% CPU (one core pegged) for as long as the fd table stayed full, a self-inflicted or attacker-induced livelock; the condition was also logged nowhere (`example/miniircd.c on_accept`)
- H-010 WARN FIXED [host-net]: Half-open TLS handshakes were unbounded: a connection is registered with the engine (uircd_accept) only after the handshake completes, so max_clients, the per-IP cap, and the registration deadline (all enforced in the engine) did not apply while handshaking. A slow or abandoned TLS handshake held an fd and an SSL object indefinitely, and one IP could hold far more than its cap, a slowloris/resource-exhaustion DoS (`example/miniircd.c on_accept (TLS branch); example/miniircd.c on_tick; example/miniircd.c drive_handshake`)
- H-011 WARN FIXED [host-net]: The EMFILE reserve-shed busy-looped under a hard process-wide RLIMIT_NOFILE with multiple workers. On exhaustion each worker freed its reserved fd to accept-and-close its backlog, but N workers share one fd table, so a worker that lost the race to reopen its reserve had no slot to shed with and respun the still-readable listener. H-009 bounded the single-worker case; this is the multi-worker process-wide case, measured with all four workers pegged (process CPU ~400 ticks/sec) under sustained exhaustion (`example/miniircd.c on_accept (EMFILE branch); example/miniircd.c on_relisten`)
- H-012 WARN FIXED [auth]: The scrypt KDF ran under the single global lock: on_readable held g_lock across uircd_recv -> cmd_pass/cmd_oper -> cfg.auth, so the ~61ms scrypt ran while holding g_lock and one login stalled every worker. Reachable with no secret (a bare PASS matches a shared * entry). Fixed: cmd_pass/cmd_oper return UIRCD_AUTH_PENDING, the host runs the KDF in a bounded pool with no lock held, and the verdict is applied later via uircd_auth_complete (`example/miniircd.c on_auth (enqueue, no KDF under lock), kdf_main (auth_compute off-lock); uircd.c cmd_pass, cmd_oper (PENDING), uircd_auth_complete`)
- H-013 OPP FIXED [auth]: Asynchronous authentication: run the KDF off the global lock in a bounded pool and deliver the login verdict at a scheduled deadline with jitter, closing both the timing enumeration (H-003) and the global-lock stall (H-012) without a decoy-KDF DoS. Implemented: UIRCD_AUTH_PENDING + uircd_auth_complete in the engine (holding the client's input until the verdict), and a bounded KDF thread pool, deadline timer, and {worker,auth_id} lifetime token in the host (`uircd.h (UIRCD_AUTH_PENDING, uircd_auth_complete); uircd.c cmd_pass, cmd_oper, uircd_auth_complete, feed_bytes/hold; example/miniircd.c on_auth, kdf_main, on_auth_deadline, auth_warmup; example/auth.c auth_lookup/auth_compute`)
- H-014 NOTE ACCEPTED [auth]: The H-003 login-timing equalization frays under a sustained login flood that saturates the KDF pool. As offered known-bad logins (which run scrypt) exceed the pool's within-deadline capacity both paths degrade together, so the gap stays small over a wide range (measured <3ms up to 8 concurrent, ~24-29ms at 16-32 concurrent on the default 2-thread pool), but at extreme saturation near the fail-closed poll cap (~64 concurrent, every login ~1s) a ~97ms known-vs-unknown separation re-emerges. Accepted: it appears only in the login-flood/bounded-CPU regime H-012/H-013 already accept (the server is fail-closing logins by then) with the signal buried in ~1s latency, and provisioning kdf-threads to the concurrent-login rate removes it (`example/miniircd.c on_auth_deadline (poll re-arm when the pool is backed up); example/miniircd.c kdf_main (pool throughput)`)
- H-015 NOTE FIXED [supply-chain]: The vendored scrypt had no verifiable provenance pin: third_party/scrypt/VENDORED.md recorded only a local checkout path (~/boris/src/scrypt) with no upstream URL, no pinned commit, and no content hash, so a reader or packager could not tell whether the in-tree crypto matched a known upstream or had drifted since vendoring, while libiox in the same tree pins an exact commit. Fixed: VENDORED.md now records the upstream project URL, a reproducible subset content-hash pin, and the recipe to recompute it, so drift from the baseline is detectable offline (`third_party/scrypt/VENDORED.md (Origin/Integrity-pin); contrast third_party/libiox/VENDORED.md (pinned commit)`)
